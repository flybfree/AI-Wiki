# Sparsely-Gated Mixture of Experts (MoE)



**Source**: [Original Paper](https://arxiv.org/abs/1701.06538)
**Shazeer et al., Google (2017)**
arXiv:1701.06538

## Abstract

The capacity of a neural network to absorb information is limited by its number of parameters. Conditional computation, where parts of the network are active on a per-example basis, has been proposed in theory as a way of dramatically increasing model capacity without a proportional increase in computation.

## Key Concepts

### The Capacity Problem
As models got bigger (thanks to scaling laws and transformer architecture), they needed more parameters. But more parameters means more computation — each additional parameter adds to inference time proportional to the model size.

MoE solves this: **use a LOT of parameters, but only activate a few per input**.

### How MoE Works
Think of a large network as a collection of specialists:

1. The network has N "expert" sub-networks (e.g., 8, 128, 2048 experts)
2. A "gating" network decides which experts to call for each input
3. Only 1 or 2 experts are activated per token (sparse)

So a 1000B parameter model might have 512 experts, each with a few billion parameters. But for each token, only 2 experts' weights are ever used. The result:

- **Training**: Can use all 1000B parameters (because all experts get trained)
- **Inference**: Only pays for 2 experts' worth of computation

### The Innovation: "Sparse" Gating
MoE isn't new conceptually — mixture models have existed in statistics. The key innovation in this paper:

- **"Sparsely-gated"**: Only 1-2 experts per token (not all of them)
- Load balancing: Ensure all experts get used, not just the "popular" ones
- This made it practical to have hundreds or thousands of experts

## Why This Changed Architecture Design

### Enabling Trillion-Parameter Models
Without MoE, you'd need to match compute budget to parameter count — so a model can't have more parameters than it can fit in compute.

With MoE: You can have TRILLIONS of parameters while only using a fraction at inference time. This is:
- TPU v2/v3 uses: MoE was deployed in Google's production translation and search systems
- Switch Transformer: Google used 16T+ parameter MoE models
- Many modern "sparse" models use MoE

### The Architecture Matching Problem
MoE shows a fundamental principle: **not every part of a model needs equal capacity**. Some domains (medical text) rarely get mentioned, so they should have dedicated experts that only activate when needed.

## For the Course

### Lesson 14 (Choosing the Right Architecture)
MoE addresses:
- **Why different data types need different architectures**: Sparse computation is the right architectural choice for language, where different inputs activate very different knowledge
- **Architecture matching to scalability needs**: Dense networks scale linearly; MoE scales super-linearly with fewer computational costs

### Lesson 16 (Deployment, Scaling)
MoE directly addresses:
- **Infrastructure needs**: MoE requires a fundamentally different hardware design (data parallelism within experts, not between)
- **Why bigger models need more coordination**: MoE shows the answer to "make it scale" is not "just add more GPUs" but "redistribute the work"
- **Infrastructure complexity**: MoE introduces routing and load-balancing complexity — infrastructure choices aren't just about "faster" but "how to divide work"

## Teaching Notes
- The "library with specialized librarians" analogy works well: many experts, but only one librarian is called for each question
- Emphasize the tradeoff: massive capacity vs computational complexity
- Connect to Chinchilla: "If Chinchilla taught us to train smaller models longer on more data, MoE teaches us to add more parameters without adding compute"
- Note: Google's T5 and Switch Transformer are the poster children for MoE
